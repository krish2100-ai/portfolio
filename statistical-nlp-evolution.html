Language AI

Evolution of Language AI

From n-grams to GPT-style language models.

Statistical natural language processing began with a simple but powerful idea: model language by estimating probabilities over sequences of words. Early systems were built on counts, context, and short-range dependencies. These methods made text understanding and generation tractable at a time when neural approaches were still in their infancy.

The trajectory is revealing. N-gram models learned the probability of a token conditioned on a short preceding window. Deep recurrent models pushed this further by learning richer latent dependencies over time. Transformers then changed the field by making attention the central mechanism, allowing a model to compare many positions in parallel and capture long-range context more effectively.

N-gram → Deep RNNs → Transformers → Foundation models (BERT, GPT-3) → Frontier models (GPT-4, Claude 3.5, Gemini 1.5) → Next-frontier (reasoning + retrieval + agents)

1. N-gram models

An n-gram model approximates the probability of a word using only the previous n − 1 words (the Markov assumption). Instead of conditioning on the entire history, it looks at a short sliding window, which makes estimation tractable from raw counts.

Sliding window: a trigram model predicts the next word from the previous two.

By the chain rule with the Markov assumption, the sequence probability factorizes as:

$$P(w_1, w_2, \dots, w_T) = \prod_{i=1}^{T} P\!\left(w_i \mid w_{i-n+1}, \dots, w_{i-1}\right)$$

and each term is estimated by maximum likelihood (relative counts, usually with smoothing):

$$P\!\left(w_i \mid w_{i-n+1}^{\,i-1}\right) = \frac{\text{count}(w_{i-n+1}, \dots, w_i)}{\text{count}(w_{i-n+1}, \dots, w_{i-1})}$$

2. Deep RNN models

Recurrent neural networks replace hand-counted probabilities with a learned hidden state that is updated at every step. The same weights are applied across time, letting the network carry information forward. LSTMs and GRUs add gates to preserve long-range signal and stabilize training.

An unrolled RNN: the hidden state h flows left to right, carrying context.

The recurrence and output at each step are:

$$h_t = \tanh\!\left(W_h h_{t-1} + W_x x_t + b\right), \qquad \hat{y}_t = \text{softmax}\!\left(W_y h_t\right)$$

3. Transformer models

Transformers drop recurrence entirely and use self-attention: every token can directly attend to every other token in the sequence. This removes the long-path bottleneck of RNNs and enables massively parallel training. Each token forms a query, and matches against keys to produce a weighted sum of values.

Self-attention: the query token attends to all tokens with learned weights.

Scaled dot-product attention combines queries \(Q\), keys \(K\), and values \(V\):

$$\text{Attention}(Q, K, V) = \text{softmax}\!\left(\frac{Q K^\top}{\sqrt{d_k}}\right) V$$

4. GPT models: pretraining and instruction fine-tuning

GPT-style models are decoder-only transformers trained to predict the next token. Training happens in stages: massive self-supervised pretraining on raw text, followed by instruction fine-tuning on curated task demonstrations, and often RLHF (reinforcement learning from human feedback) to align outputs with human preferences.

The GPT training pipeline, from raw text to an aligned assistant.

Pretraining minimizes the autoregressive negative log-likelihood over the corpus:

$$\mathcal{L}_{\text{LM}} = -\sum_{t=1}^{T} \log P_\theta\!\left(w_t \mid w_{\lt t}\right)$$

The role of the prompt

Because the model only ever predicts the next token given preceding tokens, the prompt — the text placed before the model’s turn — is the conditioning context \(w_{\lt t}\) that steers the whole generation. A pretrained model continues text; instruction tuning is what teaches it to treat the prompt as a task to follow rather than a passage to autocomplete.

This is why instruction fine-tuning data must itself be prompt-shaped. Each training and validation example is a pair of (prompt, ideal response): an instruction, optional input, and the desired output. The model is trained to maximize the likelihood of the response conditioned on the prompt, so the validation set has to contain realistic prompts too — otherwise you measure autocompletion, not instruction-following. Formally the objective shifts from \(P_\theta(w_t \mid w_{\lt t})\) to a conditional \(P_\theta(\text{response} \mid \text{prompt})\).

For reliable answers, an effective prompt is usually built from a few distinct components:

  • Role / system context — who the model should act as and any global rules.
  • Instruction — the specific task, stated clearly and unambiguously.
  • Input / context — the data, documents, or retrieved evidence to work from.
  • Examples (few-shot) — one or more demonstrations of the desired input→output mapping.
  • Output format — the expected structure (JSON, steps, length, tone) so the answer is usable.
  • Constraints — what to avoid, edge-case handling, and stopping conditions.

Matching the structure of these components between fine-tuning data and inference is what makes prompting predictable: the model has learned the shape of a good prompt→response pair and generalizes to new ones.

When the model hallucinates

A hallucination is when the model produces text that is fluent and confident but factually wrong, unsupported, or fabricated — invented citations, made-up numbers, or claims that were never in its training data or the prompt. It happens because the model is optimized to produce probable-sounding next tokens, not verified truth: it has no built-in notion of “I don’t know,” so it fills gaps with the most plausible continuation.

Hallucinations become more likely when:

  • Knowledge is missing or stale — the question is outside the training data or about events after the cutoff, so there is no grounded answer to recall.
  • The prompt is vague or underspecified — with little context, the model guesses intent and invents specifics to fill the blanks.
  • Rare or long-tail facts — obscure names, exact dates, statistics, or citations are weakly represented, so the model interpolates a plausible-looking value.
  • Long, multi-step reasoning — small errors compound over many tokens, and the model may confidently continue down a wrong path.
  • Leading or false-premise prompts — if the prompt assumes something untrue, the model tends to go along with it rather than challenge it.
  • High decoding randomness — a high sampling temperature increases variety but also the chance of drifting away from grounded facts.

This limitation is exactly what motivates the retrieval and agent techniques in the next section: by grounding the model in retrieved evidence (RAG) and letting it verify with tools, we reduce the space in which it has to guess.

5. Retrieval and Agents

Bigger models alone hit limits: they hallucinate, lack up-to-date or private knowledge, and struggle with long multi-step tasks. The next frontier augments the model with external memory (retrieval) and the ability to act (tools and agents).

Vector databases

A vector database stores text (documents, chunks, facts) as high-dimensional embeddings — numeric vectors where semantically similar items are close together. At query time, the query is embedded and the database returns the nearest vectors, enabling semantic search rather than keyword matching.

Documents are embedded into a vector space; the query retrieves its nearest neighbours.

Similarity is typically measured by cosine similarity between embeddings \(a\) and \(b\):

$$\text{sim}(a, b) = \frac{a \cdot b}{\lVert a \rVert \, \lVert b \rVert}$$

Retrieval-Augmented Generation (RAG)

RAG connects a language model to a vector database. The user query retrieves the most relevant chunks, which are injected into the prompt as context. The model then answers grounded in that retrieved evidence — reducing hallucination and allowing fresh or private knowledge without retraining.

RAG pipeline: retrieve relevant context, then generate a grounded answer.

Conceptually, RAG marginalizes over the retrieved documents \(d\):

$$P(y \mid x) \approx \sum_{d \,\in\, \text{top-}k} P(y \mid x, d)\, P(d \mid x)$$

Agentic systems

An agentic system lets the model do more than answer in one shot: it can plan, call tools (search, code, APIs, databases), observe results, and iterate toward a goal. The model becomes a controller in a loop rather than a single function call. Three common design paradigms:

How the prompt selects the next action. At every step the agent builds a prompt that lists the goal, the history so far, and the set of available tools/actions. The model then scores possible continuations and, because generation is probabilistic, effectively ranks the candidate actions by likelihood \(P_\theta(\text{action} \mid \text{prompt})\). The highest-scoring, well-formed candidate (for example a specific tool call with arguments) is chosen and executed. So the prompt does double duty: it both constrains what actions are legal by enumerating them, and guides the selection by providing the context that makes one action more probable than the rest. Its result (the observation) is appended to the prompt, and the cycle repeats — each action choice conditioned on an ever-growing context.

Tool-call loop (exploratory)

The simplest agent: the model decides whether to call a tool, sees the result, and repeats until it can answer. It is flexible and good for open-ended exploration, but can wander without a clear plan.

Tool-call loop: the model calls a tool, observes the result, and repeats.

ReAct (Reasoning + Acting)

ReAct interleaves explicit reasoning traces with actions: the model writes a Thought, takes an Action, reads an Observation, and loops. Making the reasoning visible improves interpretability and helps the agent recover from mistakes.

ReAct cycle: Thought → Action → Observation, repeated until the answer.

Plan-and-Execute

For complex, compositional, and largely deterministic tasks, a planner first decomposes the goal into an ordered list of steps, and an executor carries them out (often calling tools). Separating planning from execution gives structure, predictability, and easier verification.

Plan-and-Execute: a planner emits ordered steps that an executor runs in turn.

These paradigms are not mutually exclusive — real systems mix them: a Plan-and-Execute agent may run a ReAct loop inside a single step, and both rely on tool calls and RAG for grounding. The through-line of the whole story is abstraction: from counts, to learned sequences, to attention, and finally to reasoning systems that retrieve knowledge and act in the world.

6. Guardrails for practical LLMs and agents

Because a raw model can hallucinate, leak data, or be manipulated — and an agent can additionally take actions in the world — production software wraps both in guardrails: checks and controls that make behaviour safe, predictable, and auditable. The model and the agent are treated as untrusted components, and the surrounding system enforces the rules.

Model-level guardrails

These constrain what a single model call is allowed to receive and produce:

  • Input validation & prompt-injection defense — sanitize and constrain user input, and isolate untrusted content (retrieved docs, tool output) so it cannot override system instructions.
  • Output validation & schema enforcement — require structured output (e.g. JSON), validate it against a schema, and reject or retry on malformed responses before they reach downstream code.
  • Grounding & citations — force answers to be backed by retrieved sources (RAG), and verify claims against those sources to catch fabrication.
  • Content safety & moderation — filter toxic, unsafe, or policy-violating content on both the input and the output using moderation classifiers.
  • PII & secret protection — detect and redact personal data and credentials, and prevent the model from echoing sensitive context or training data.
  • Scope & topic limits — restrict the assistant to its intended domain and refuse out-of-scope or disallowed requests.
  • Uncertainty & fallbacks — let the model say “I don’t know,” route low-confidence cases to a human, and provide safe default responses.

Agent-level guardrails

Agents act over many steps and call tools, so they need additional controls around the loop:

  • Tool allowlisting & permissions — restrict which tools/APIs the agent may call, with least-privilege scopes per task.
  • Action approval for high-risk steps — require human confirmation before irreversible or sensitive actions (payments, deletes, emails, deploys).
  • Sandboxing & isolation — run code and tool execution in isolated, resource-limited environments that cannot touch production data directly.
  • Loop & budget limits — cap iterations, tool calls, tokens, and wall-clock time to stop runaway or looping agents.
  • Plan validation & step checks — verify each proposed step against policy and preconditions before executing, and re-plan on failure.
  • State & memory hygiene — prevent untrusted tool output from silently rewriting goals, and keep trusted instructions separate from working memory.
  • Observability & kill switch — trace every thought, action, and observation, with the ability to pause or abort an agent mid-run.

System-level guardrails

  • Rate limiting & cost controls — cap requests and spend to prevent abuse and runaway usage.
  • Logging, monitoring & evaluation — record prompts, actions, and outputs; track quality and safety metrics; and continuously test against a regression suite.
  • Access control & audit — authenticate users, authorize actions, and keep an auditable trail of what the system did and why.

Together these turn a probabilistic text generator into a dependable software component: the model and agent propose, but the guardrails decide what is allowed to happen.

7. Foundation, frontier, and next-frontier models

Stepping back from the individual techniques, the models themselves are often grouped less by architecture and more by scale, capability, and role. Three overlapping tiers are worth distinguishing.

Foundation models

A foundation model is a large model pretrained on broad, unlabeled data that can be adapted (via fine-tuning or prompting) to many downstream tasks. The value is in the reusable representations, not a single task. Examples: BERT, GPT-2/GPT-3, T5, RoBERTa, CLIP, and early open models like LLaMA. In the evolution path, foundation models are the first products of the transformer era — the shift from task-specific training to general pretraining.

Frontier models

A frontier model is a current, state-of-the-art, general-purpose model at the cutting edge of capability and scale — typically multimodal and heavily aligned. The term also carries a safety connotation (“frontier AI”), because these systems can show emergent, hard-to-predict abilities. Examples: GPT-4 / GPT-4o, Claude 3.5, Gemini 1.5, and Llama 3.1 405B. They sit after foundation models on the path: same architecture lineage, but far larger, instruction-tuned, and RLHF-aligned.

Next-frontier models

Next-frontier models push beyond one-shot answering toward reasoning, retrieval, and autonomy. They add test-time reasoning (deliberate chain-of-thought trained with RL), long context, native tool use, and agentic loops — the retrieval and agent techniques covered above. Examples: OpenAI o1 / o3 (reasoning models), Claude with computer use, and Gemini 2.0 agentic systems. This is the leading edge of the evolution path.

Aspect Foundation Frontier Next-frontier
Training Self-supervised pretraining on broad data Pretraining + instruction tuning + RLHF at massive scale, multimodal Adds RL for reasoning, tool-use training, long-context and agentic objectives
Evaluation Transfer benchmarks (GLUE, SuperGLUE), fine-tune then test Broad zero/few-shot suites (MMLU, HumanEval, MATH) + safety red-teaming Agentic / task-completion benchmarks (SWE-bench, GAIA, ARC-AGI), long-horizon success
Capabilities Reusable representations, transfer learning Strong general reasoning, coding, multimodal understanding Multi-step reasoning, retrieval grounding, tool use, autonomous task execution
Examples BERT, GPT-3, T5, CLIP, LLaMA GPT-4o, Claude 3.5, Gemini 1.5, Llama 3.1 405B o1 / o3, Claude computer use, Gemini 2.0 agents

The tiers are cumulative rather than exclusive: a next-frontier system is still built on a frontier model, which is itself a scaled-up, aligned foundation model. What changes at each tier is how much of the intelligence comes from training the weights versus orchestrating reasoning, retrieval, and actions at run time.
